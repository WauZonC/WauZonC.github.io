# 人工操作手册：增添 / 修改 / 提交

> **这份文档是给「人」看的**，与 [PLAN.md](../PLAN.md) 的分工是：
> - **[PLAN.md](../PLAN.md)** 是**唯一权威设计文档**，回答「**为什么**这么设计」「**允许**改什么」——ADR、路由契约、schema、轨道边界、风险门禁都在那里。
> - **本文**只回答「**具体怎么敲**」——你要加一篇博客、改一段介绍、把改动发上线，照着这里做即可。
>
> 两者冲突时**以 PLAN.md 为准**，并请顺手修正本文。
> 命令均以 **`D:\WZC\mypage\WauZonC.github.io`** 为工作目录（下文若写 `pnpm xxx`，请先 `cd` 到该目录）。

## 0. 先看这里：我该走哪条路？

```
我要做的事
├─ 加 / 改 / 删 一篇博客或一个项目          → 第 1、2 章（改 Markdown）
├─ 加一张配图                              → 1.5
├─ 换背景照片 / 指定某天用某张背景          → 第 3 章（拖进目录 + 改 config.ts 的 rules）
├─ 只改一两个字（错别字）                  → 第 2 章，然后第 5 章（可跳过立项）
├─ 改配色 / 玻璃质感 / 版式                → 本文不管，见 PLAN.md §10.2 轨道 B（要动 CSS，须立项）
├─ 加新页面 / 新功能 / 新内容集合          → 本文不管，见 PLAN.md §10.2 轨道 C（须先立项，可能要立 ADR）
└─ 把上面的改动发上线                      → 第 5 章（提交 + 推送 + 等 Actions）
```

**一句话心法**：这个站点的内容是**纯 Markdown 驱动**的。加一篇博客 = **加一个 `.md` 文件**，**永远不需要改任何 `.astro` 页面代码**（这是 PLAN.md 里反复强调的 **G3 契约**）。

## 1. 增添内容

### 1.1 新增一篇博客

**写作用域**：`src/content/blog/<slug>.md`（配图另加 `public/images/`）

**第 1 步：确定文件名（= URL）**

文件名就是网址：`src/content/blog/cuda-notes.md` → `https://wauzonc.github.io/blog/cuda-notes/`

- ✅ 只用**小写字母、数字、连字符**：`my-first-post.md`、`cs61b-notes-2.md`
- ❌ **不要用中文文件名**，不要用空格、下划线、大写
- ⚠️ **文件名一旦发布就不要改** —— 改了旧网址立刻 404，而本站**没有**重定向机制（见 PLAN.md §7 风险表）

**第 2 步：建文件，写 frontmatter**

在 `src/content/blog/` 下新建 `<slug>.md`，开头必须是 frontmatter：

```markdown
---
title: '标题：写清楚这篇讲什么'
description: '一句话摘要，会出现在 /blog 列表和首页「最新文章」，也是搜索引擎的 meta description。'
pubDate: 2026-10-12
tags:
  - 标签一
  - 标签二
draft: false
---

正文从这里开始，用 Markdown 写。
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `title` | ✅ **必填** | 标题 |
| `description` | ✅ **必填** | 摘要，列表与 meta description 都用它 |
| `pubDate` | ✅ **必填** | 发布日期，`YYYY-MM-DD`。**决定 `/blog` 列表与首页「最新文章」的排序** |
| `updatedDate` | 可选 | 更新日期 |
| `tags` | 可选 | 标签数组，默认 `[]` |
| `draft` | 可选 | 默认 `false`；设 `true` 则**不参与构建**（适合先提交半成品） |
| `cover` | 可选 | 封面图路径，相对 `public/` |

> ⚠️ **三个最常见的坑**
> 1. **`pubDate` 不要写未来日期** —— 它会长期占着「最新文章」第一位。
> 2. **漏了必填字段 → 构建失败**。这不是环境坏了，是 schema 校验按设计拦住了你：构建会**非 0 退出**，日志里有 `[InvalidContentEntryDataError]`，并告诉你**哪个集合、哪个条目、哪个字段**错了。照着修即可。
> 3. **frontmatter 的 `---` 必须是文件第一行的三个连字符**，前后不能有空行或 BOM。
> 4. **`title` / `description` 里含冒号时要用引号包起来**（如上面示例的 `'标题：...'`），否则 YAML 会解析失败。

> Obsidian 用户注意：正文里的 `[[双链]]` **不会**生效，必须改成普通链接或纯文本（P4 起的约定）。

**第 3 步：写正文**

就是普通 Markdown。标题、列表、代码块、表格、引用都支持（代码高亮由 Shiki 构建期生成）。

**第 4 步：本地看效果**

```bash
pnpm dev        # 打开 http://localhost:4321/blog/<slug>/ 
```

**第 5 步：构建验证**

```bash
pnpm build
```

期望：**退出码 0**，且页面数从 `13` 变成 `14`（`14 page(s) built`）。然后去第 4 章提交。

### 1.2 新增 / 修改一个项目条目

**写作用域**：`src/content/projects/<slug>.md`（配图另加 `public/images/`）

```markdown
---
title: 项目名
description: 一句话说明这个项目是什么。
tech:
  - Astro
  - Python
repoUrl: https://github.com/WauZonC/<repo>
demoUrl: https://example.com
featured: true
order: 90
cover: /images/my-project.png
---

正文：介绍背景、做了什么、结果如何。
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `title` | ✅ **必填** | 项目名 |
| `description` | ✅ **必填** | 一句话说明 |
| `tech` | 可选 | 技术栈标签数组，默认 `[]` |
| `repoUrl` | 可选 | 仓库地址，**必须是完整 URL**（`https://...`） |
| `demoUrl` | 可选 | 演示地址，**必须是完整 URL** |
| `featured` | 可选 | 默认 `false`；**只有 `true` 才出现在首页「精选项目」** |
| `order` | 可选 | 默认 `0`；**数字越大在 `/projects` 排得越前** |
| `cover` | 可选 | 卡片配图，相对 `public/` 的路径 |

> `repoUrl` / `demoUrl` 走 `z.string().url()` 校验：写 `github.com/xxx`（缺 `https://`）会**构建失败**。

**已知待补（来自 PLAN.md §10.2 A2）**：手势识别项目缺配图；「本站」项目卡片可补 `repoUrl = https://github.com/WauZonC/WauZonC.github.io`。

### 1.3 新增英文版内容

英文站是 `/en/` 前缀的**真实路由镜像**，靠**同名即同 slug** 实现语言互跳。
给某篇中文博客补英文版的**唯一要求**：在 `src/content/blog-en/` 放一个**逐字同名**的文件。

```
src/content/blog/cuda-notes.md      →  https://wauzonc.github.io/blog/cuda-notes/
src/content/blog-en/cuda-notes.md   →  https://wauzonc.github.io/en/blog/cuda-notes/
```

- frontmatter 字段与中文**完全一致**（两套集合共用同一份 schema），正文写英文
- **文件名必须逐字相同**。不一致**不会报错**，但语言按钮会退回列表页（跳不到对应文章），属于静默失效
- 项目同理：`src/content/projects-en/<同名>.md`
- **不需要改任何 `.astro` 文件**
- 英文 404 的地址是 **`/en/404/`**，**不是** `/en/404.html`（Astro 只把根目录的 `404.astro` 特殊化为 `404.html`）

> ⚠️ **已知噪音**：`blog-en/` / `projects-en/` 为空时，构建会打印
> `[glob-loader] No files found matching "**/*.md"` 与 `The collection "blogEn" does not exist or is empty`。
> **退出码仍是 0，不是故障**；放入第一篇 `.md` 后即消失。

### 1.4 修改已有内容

直接编辑对应文件即可，流程与新增完全一样（改完 → `pnpm dev` 看 → `pnpm build` → 第 4 章提交）。

- **改正文**：随便改，没有副作用。
- **改 `pubDate`**：会改变排序，慎改。
- **改 `title` / `description`**：安全，只影响展示与 SEO。
- **改文件名（slug）**：⚠️ **等于改了网址** —— 旧链接 404，且**本站没有重定向**。除非你同时按 PLAN.md §7 的做法加一个跳转页，否则**不要改**已发布条目的文件名。
- **改英文条目**：注意保持与中文**同名**。

### 1.5 加配图

1. 把图片放到 `public/images/` 下（例如 `public/images/my-post-diagram.png`）
2. 正文里用**绝对路径**引用：`![说明](/images/my-post-diagram.png)`

> ⚠️ **图片入库前必须剥离 EXIF**
> 本站**公开**，照片的 EXIF 里可能带 **GPS 坐标、拍摄时间、设备型号** —— 提交即等于公开。仓库根目录的 `backgroud_chunk.jpg` 就是因为带 GPS 而被 `.gitignore` 精确忽略的，**永远不要提交它**。
>
> 清 EXIF 的方法（Windows 自带 .NET，无需装任何东西）：
> ```powershell
> Add-Type -AssemblyName System.Drawing
> $src = 'C:\path\to\原图.jpg'
> $dst = 'D:\WZC\mypage\WauZonC.github.io\public\images\my-post-diagram.jpg'
> $img = [System.Drawing.Image]::FromFile($src)
> $bmp = New-Object System.Drawing.Bitmap $img
> $img.Dispose()
> $bmp.Save($dst, [System.Drawing.Imaging.ImageFormat]::Jpeg)   # Save() 会丢弃 EXIF
> $bmp.Dispose()
> ```
> **实测对照（2026-10-12，本机）**：这张写法的确能清掉 EXIF/GPS ——
> 根目录原图 `backgroud_chunk.jpg` 有 **67** 项属性（其中 `0x0001`–`0x0007` 正是 GPS 标签、`0x0112` 是相机方向、`0x0132` 是拍摄时间），
> 而清空后入库的 `public/images/background.jpg` 只剩 **2** 项（`0x5090` / `0x5091`，即颜色空间标记），**GPS 全无**。
>
> 验证（`count` 不会变成 `0`：JPEG 至少保留上表那 2 项颜色空间标记，**只要远小于原图、且不含 `0x0001`–`0x0007` 就是干净的**）：
> ```powershell
> $i = [System.Drawing.Image]::FromFile('D:\...\public\images\my-post-diagram.jpg')
> $i.PropertyIdList.Count                      # 干净时应为 2 左右（原图是 67）
> $i.PropertyIdList | ForEach-Object { '0x{0:X4}' -f $_ }   # 不应出现 0x0001..0x0007（GPS）
> $i.Dispose()
> ```
> 另外建议先**压到合理体积**（现有背景图 2560×1920 压到 1.6 MB 才入库）。

## 2. 删除 / 停用内容

| 想做什么 | 怎么做 | 注意 |
|---|---|---|
| **临时下线一篇文章**（保留文件） | 把 frontmatter 改成 `draft: true` | 最安全。文件还在，随时改回 `false` 复活 |
| **彻底删除一篇文章** | 删除该 `.md` 文件 | ⚠️ 它的网址会 **404**，且**不可逆**（见下） |
| **删除配图** | 删除 `public/images/<name>.png`，并**搜一遍谁在引用它** | 漏删引用会出现裂图 |

> ⚠️ **删除是不可逆操作的边界**：站点是公开的，已发布的网址可能已被搜索引擎收录、被别人收藏或引用。
> 按 PLAN.md §10.1 规则 5，**删除文件属于「先停下来问用户」的操作**。如果只是想让它消失，**优先用 `draft: true`**。

**首选做法**：能 `draft: true` 就不要删文件。

## 3. 背景照片（换背景 / 按日期固定某张）

> 由 PLAN.md **ADR-12**（维护任务 M-4）定义。**你只需要记住三件事**：
> 照片放在 `public/images/backgrounds/`、文件名叫什么就是它的 id、哪天用哪张写在 `src/backgrounds/config.ts`。
> 页头右上角那个「换背景」按钮是给访客随手换一张用的（**只影响他自己的浏览器**，不改站点）。

### 3.1 上传一张自己喜欢的照片

**最省事：直接把图片文件拖进 `public\images\backgrounds\` 文件夹**，然后做两件事：

1. **给它改成规范的文件名**：`<id>.jpg`，id 只能是**小写字母、数字、连字符**（如 `sunset-sea.jpg`）。
   文件名就是配置里要写的 `bg` 值。
2. **运行同步命令**（把目录扫进索引，并校验配置）：

```bash
cd D:\WZC\mypage\WauZonC.github.io
pnpm sync:backgrounds
```

> ⚠️ **拖进去的原始照片带 EXIF/GPS**（拍摄地点、时间、手机型号）。本站仓库是**公开**的，
> 提交原图等于公开你的拍摄位置 —— 第一张背景图就曾带着 GPS `36°02′59.4″N / 120°20′36.0″E`（见 ADR-11）。
> 所以**更推荐**下面这条命令，它会自动剥掉全部元数据、压到 2560px 长边再入库：

```bash
pnpm add:background -- "D:\照片\我拍的.jpg" --id sunset-sea
```

- 想保留拍摄方向（竖拍照片）再加 `--rotate`（把 EXIF 方向烘焙进像素后再删元数据）。
- 命令末尾会打印 `EXIF after : 0 tags / 0 GPS entries -> CLEAN`，**必须是 CLEAN**。
- 若照片偏亮，它会提示正文对比度可能不足 —— 那就换一张或先在别处压暗，见 3.4。
- 名字已存在时会拒绝覆盖；确实要替换就加 `--force`（旧版本仍留在 Git 历史里，不可回收）。

### 3.2 指定「某一天用哪张」——改 `src/backgrounds/config.ts`

打开 `src/backgrounds/config.ts`，找到 `rules` 数组，按**从上到下**的优先级写规则。
`on` 有三种写法（写错会被 `pnpm sync:backgrounds` 直接拦下）：

| 写法 | 含义 | 例子 |
|---|---|---|
| `'YYYY-MM-DD'` | **只有这一年这一天** | `{ on: '2027-01-01', bg: 'new-year' }` |
| `'MM-DD'` | **每年的这个月-日**（节假日用这种） | `{ on: '10-01', bg: 'national-day' }` |
| `'0'`–`'6'` | 每星期几（**单个数字**，0 = 周日、6 = 周六） | `{ on: '6', bg: 'weekend' }` |

```ts
rules: [
  { on: '2027-01-01', bg: 'new-year' },   // 只有 2027 年元旦用这张
  { on: '01-01',      bg: 'new-year' },   // 以后每年元旦都用这张
  { on: '10-01',      bg: 'national-day' },// 每年国庆
  { on: '02-10',      bg: 'spring-festival' }, // 春节想跨多天就写多行指向同一张
  { on: '02-11',      bg: 'spring-festival' },
  { on: '02-12',      bg: 'spring-festival' },
],
```

改完**必须**再跑一次同步 + 一次构建：

```bash
pnpm sync:backgrounds     # 校验 id 是否存在、规则顺序是否合理，并刷新索引
pnpm build                # 规则会烘焙进页面，线上要生效必须重新构建（推送即自动构建）
```

**两个容易踩的坑（命令会帮你拦下）**
1. 精确日期必须写在同年同月同日的 `'MM-DD'` **之前**，否则前者永远轮不到。
2. 星期几只能写 `'6'`，**不要写 `'06'`** —— 那会被当成「6 月某日」的残缺写法而永不命中。

### 3.3 按钮与「刷新不变」的语义

| 场景 | 结果 |
|---|---|
| 首次访问（没点过按钮） | 按**你所在设备当天的日期**取图；同一天不管刷新几次、跳几次页都是**同一张** |
| 点了「换背景」 | 从照片池里**随机**抽一张（排除当前那张，所以点了必定换），写入该浏览器本地存储 |
| 点完再刷新 / 跳页 | **保持你点的那张** |
| 第二天再打开 | 回到「按日期取图」（也就是所谓「当日有效」，可在 `config.ts` 用 `persist: 'forever'` 改成永不变） |
| 日期规则都没命中 | 按 `fallback` 兜底（`'hash'` 稳定打散 / `'cycle'` 按天轮转），**同一天恒定同一张** |

> 访客点按钮**不会**影响你或别的访客 —— 它只写进访客自己的浏览器 `localStorage['bg-v1']`，
> 服务端没有任何状态。你改了规则并推送后，访客第二天打开就会看到新规则生效。

### 3.4 两张「门禁」命令（导入新照片后建议都跑一遍）

```bash
pnpm check:backgrounds        # 配置与目录是否一致（漏跑 sync 会在这里报错）
node tmp/check_bg_contrast.py # 逐张量测：正文/次要文字在玻璃上是否过 WCAG AA（≥4.5）
```

`tmp/` 里的脚本是**验收探针**，不入库、可随时重跑；它们的存在理由是 ADR-11 踩过的坑：
照片一变亮，浅色文字叠在深色玻璃上就可能读不清，而这**肉眼在浅色环境下看不出来**。

### 3.5 关于浅色 / 深色

**深浅色切换已按你的要求静默**（页头不再有那个按钮，站点恒定浅色外观）。
代码**一行都没删**：`src/components/ThemeToggle.astro`、它的内联脚本、`global.css` 里两处深色令牌都还在。
想恢复只需把 `src/backgrounds/config.ts` 里的 `THEME_TOGGLE_ENABLED` 从 `false` 改成 `true`（改这一行即可）。
详见 ADR-12。

## 4. 改完之后的本地自检（R1–R5）

> PLAN.md §10.4 要求**每次推送前**都跑一遍。下面是最小可用的一组命令。
> 基线（2026-10-11 实测）：**13 个页面 / 博客 3 篇 / 项目 4 条 / `dist` 内 `.js` 为 0**。

### R1 — 构建通过

```bash
pnpm build
```

期望：**退出码 0**，日志末尾形如 `[build] 13 page(s) built in 2.24s` + `[build] Complete!`。
加了 1 篇博客就应该是 `14 page(s) built`。

### R2 — 页面数与内容数对得上

```powershell
(Get-ChildItem -Recurse -File -Filter *.html dist).Count          # 期望 13（+新增文章数）
(Get-ChildItem -File src\content\blog\*.md).Count                 # 博客篇数
(Get-ChildItem -File src\content\projects\*.md).Count             # 项目条数
```

### R3 — 零客户端 JS 没被破坏

```powershell
(Get-ChildItem -Recurse -File -Filter *.js dist).Count            # 期望 0
```

> ⚠️ **正确理解这条命令**：它**仍然应该是 `0`**，但**「零客户端 JS」自 ADR-9 起已不再是字面事实** —— `src/**` 里有 3 段 `is:inline` 内联脚本（首屏主题/背景、背景按钮；见 ADR-9 与 ADR-12），每个页面的 HTML 里都能看到 **3** 个 `<script>`。
> `is:inline` 不产出 `.js` 文件，所以命令返回 0。
> **禁止**把这条命令改写成「HTML 里没有 `<script>`」来掩盖这个性质变化（ADR-9 明文要求）。

### R4 — 无横向滚动

```bash
pnpm preview        # 起服务；也可以直接对 dist 产物做探针（见下）
```

> ⚠️ **这一条有两个真实的测量陷阱，会让你得到假结论**（都已被实际踩到）：
> 1. **headless Edge/Chrome 有约 504px 的最小窗口宽度**。`--window-size=320` 实测拿到的是 `innerWidth=504`，据此算出的「320px 无横向滚动」**全是假的**。要测真实窄屏，只能靠**精确 CSS 宽度的 iframe** 或 **CDP 设备模拟**。
> 2. **iframe 上的滚动条会吃掉约 15px**。`<iframe width=320>` 里的 `documentElement.clientWidth` 其实是 **305**，于是 320px 的判定被悄悄抬高成 305px 判定，结论会**偏乐观**（假阳性）。

**推荐做法（CDP 设备模拟，最准，无滚动条干扰）**：把页面按真实视口宽度（320 / 390 / 768 / 1440）逐条测量
`documentElement.scrollWidth <= documentElement.clientWidth`。可复用脚本见 `tmp/cdp_overflow.py`（`tmp/` 已被 `.gitignore` 忽略，不会入库）。

**快速做法（注入式，够用）**：在 `dist` 里复制一份目标页面，在 `</body>` 前注入一段测量脚本，
再以 `--headless --dump-dom --allow-file-access-from-files` 打开并读取结果。注意探针页必须放在 `dist` 根、
且 iframe 的 `src` 要用**相对路径**（写 `/about/` 会被解析成文件系统根，`contentDocument` 直接不可读）。

**已知未修问题（真实存在，2026-10-12 实测）**：
`/about/` 在**真实 320px 视口**下会横向溢出约 **3px**（`scrollWidth=323` / `clientWidth=320`）。
根因是页面里那个邮箱链接：

```html
<a href="mailto:zhongchangwang25@stu.pku.edu.cn">zhongchangwang25@stu.pku.edu.cn</a>
```

它在 320px 下宽 **274.6px**，是个**不可断行**的超长 token，需要 323px 才放得下 → 溢出到圆角外。
**PLAN.md v2.5 / M-1·M-2 记录的「320px 也全过」是上述陷阱导致的假阳性**，本文按实测更正。
修复方向（未实施，需按轨道 B 立项）：给正文链接/段落加 `overflow-wrap: anywhere`（或对邮箱单独设 `word-break: break-all`），
再按无横向滚动重新验收。**改 `src/styles/global.css` 属轨道 B，不要在纯文档改动里顺手改。**

### R5 — 无隐私 / 版权泄漏（**最不能省**）

对 `src/`、`public/`、`dist/` 扫描**硬红线** → 期望 **0 命中**：
手机号、18 位身份证、学号、成绩排名、政治面貌、住址、他人姓名清单、含正脸的合影。

```powershell
# 取待扫文件（-Path 传数组时 -Include 不生效，必须先 Get-ChildItem 再管道给 Select-String）
$files = Get-ChildItem -Recurse -File -Path src,public,dist `
                       -Include *.md,*.astro,*.ts,*.html,*.json,*.css -ErrorAction SilentlyContinue

foreach ($p in $patterns) {
  $hits = $files | Select-String -Pattern $p -ErrorAction SilentlyContinue

```

## 5. 提交与发布（人工版）

> 远端已配置为 **SSH**：`git@github.com:WauZonC/WauZonC.github.io.git`，分支 **`main`**。
> 推送到 `main` 会由 `.github/workflows/deploy.yml` **自动构建并部署**到 <https://wauzonc.github.io>。

### 5.1 看当前状态

```bash
git status                    # 哪些文件改了 / 新增了
git diff                      # 具体改了什么（还没 add 的）
git log --oneline -5          # 最近的提交，参考下别人的措辞
```

### 5.2 先确认你没打算提交不该提交的东西

**`git add` 之前务必扫一眼 `git status`**。以下内容**绝不能入库**（`.gitignore` 已兜住大部分，但别用 `-f` 强行加）：

| 不该提交 | 原因 |
|---|---|
| `node_modules/`、`dist/`、`.astro/` | 依赖与构建产物，仓库会膨胀 |
| `backgroud_chunk.jpg`（仓库根目录） | **原图带 GPS 坐标**，公开即暴露拍摄地点 |
| `p4-review/`、`tmp/` | 待审批草稿与临时探针脚本 |
| `.env`、`.obsidian/`、`.claude/` | 密钥与编辑器私有配置 |

> 🚨 **绝对不要用 `git add -A` 或 `git add .`** —— PLAN.md §10.4 明确要求**按路径精确 add**，避免把 `p4-review/`、临时文件误纳。
> 也**不要**用 `git add -f` 去绕过 `.gitignore`（PLAN.md §8.1 明文禁止）。

### 5.3 暂存并提交

```bash
# 只加你真正改过的路径，一个一个写清楚
git add src/content/blog/cuda-notes.md

# 加配图的话
git add public/images/my-post-diagram.png

# 看一眼即将提交的内容（强烈建议）
git diff --cached

# 提交
git commit -m "feat(blog): 新增《标题》"
```

**提交信息格式**（沿用仓库现有风格，冒号前是类型）：

| 前缀 | 用于 | 真实例子（见 `git log`） |
|---|---|---|
| `feat(blog):` | 新增内容 | `feat(ui): 全站改为 iOS 26 风格...` |
| `feat(ui):` | 新增功能 / 界面改动 | `feat(ui): 页头新增中英文与浅色/深色切换按钮` |
| `style:` | 纯样式调整 | — |
| `fix:` | 修 bug | — |
| `modify(src/content):` | 修改已有内容 | `modify(src/content): 修改手势识别项目简介，增加免责声明` |
| `docs(plan):` | 文档 / PLAN 回填 | `docs(plan): 回填 v2.3 发布记录...` |

> 提交信息里**不要写真实姓名、学号、手机号**等隐私内容（提交历史同样是公开的）。

### 5.4 推送

```bash
git push origin main
```

- ⚠️ **推送前确认 `git log origin/main..HEAD` 只有你预期的提交**（避免把别处遗留的提交一起推上去）。
- 若报 `rejected`（远端有别人的新提交）：先 `git pull --rebase` 再推，**不要** `push --force`。

### 5.5 等 Actions 并做线上核验（R6）

1. 打开 **<https://github.com/WauZonC/WauZonC.github.io/actions>**，等最新一次运行的 **Build 与 Deploy 两个作业都变绿**（约 1 分钟）。
   - ⚠️ **纯文档改动也会触发一次部署**，这是预期行为。
   - ⚠️ 若 `deploy` 失败，常见原因是仓库 **Pages 来源**不是 GitHub Actions（应为 `Settings → Pages → Source = GitHub Actions`）。
2. 线上抽查：

```powershell
# 关键路由返回 200（-UseBasicParsing 避免非交互环境下的 IE 首次运行报错）
foreach ($u in @('/', '/about/', '/blog/', '/projects/', '/blog/cuda-notes/')) {
  $r = Invoke-WebRequest -Uri "https://wauzonc.github.io$u" -Method Head -UseBasicParsing
  "HEAD {0,-22} -> {1}" -f $u, $r.StatusCode
}
# 不存在的路径应当返回 404 状态（GitHub Pages 会用根 404.html 渲染自定义内容）
try { Invoke-WebRequest -Uri 'https://wauzonc.github.io/no-such-page-xyz/' -Method Head -UseBasicParsing -ErrorAction Stop }
catch { "不存在的路径 -> {0}（期望 404）" -f $_.Exception.Response.StatusCode.value__ }

# 线上首页与本地 dist 产物是否逐字节一致（SHA-256 应完全相同）
$r = Invoke-WebRequest -Uri 'https://wauzonc.github.io/' -UseBasicParsing
$tmp = "$PWD\tmp\_online_index.html"
[System.IO.File]::WriteAllBytes($tmp, $r.RawContentStream.ToArray())   # 必须按原始字节写，否则换行会被改写
"线上 SHA256: $((Get-FileHash $tmp -Algorithm SHA256).Hash)"
"本地 SHA256: $((Get-FileHash dist\index.html -Algorithm SHA256).Hash)"
Remove-Item $tmp -Force
```

> 实测（2026-10-12）：`/blog/cuda-notes/`、`/`、`/404.html` 均 **200**，不存在路径 **404**；
> 线上首页与本地 `dist/index.html` **同为 21742 字节、SHA-256 完全相同**
> （`16ADD1C9…9237AE`）—— 说明线上就是本地构建产物。

3. 页面本身也点开看一眼（中文是否正常、新文章是否出现在 `/blog` 列表）。

### 5.6 回滚（如果发出去的东西不对）

```bash
git revert <出问题的提交 sha>      # 生成一个「反向提交」
git push origin main               # 推送后 Actions 会重建，线上自动回到上一版
```

- **首选 `git revert`**：安全、保留历史。
- ⚠️ **只有在确需抹掉历史时才用** `git reset --hard` + `push --force-with-lease`，而且**必须先征得用户同意**（PLAN.md §10.4）。
- ⚠️ **内容泄漏类事故**：`revert` 能撤下页面，但**推到公开仓库的内容已被缓存与归档，无法真正消除**。所以 4.2 和 R5 的检查必须在推送**之前**做。

## 6. 常见问题（照着查）

| 症状 | 原因 | 怎么办 |
|---|---|---|
| `pnpm build` **非 0 退出**，日志有 `[InvalidContentEntryDataError]` | frontmatter 缺必填字段或类型不对 | **这是预期行为**，不是环境故障。看日志里的集合名、条目名、字段名去修。Windows 上还可能显示退出码 `-1073740791` / `0xC0000409`，同样是校验中止，不是崩溃 |
| 构建有 `[glob-loader] No files found matching` / `The collection "blogEn" ... is empty` | 英文集合还是空的 | **退出码仍是 0，不是故障**。放入第一篇英文 `.md` 后消失 |
| 新文章没出现在列表里 | ① `draft: true` ② `pubDate` 写成了未来日期 ③ 文件不在 `src/content/blog/` 下 | 逐条检查 |
| 文章网址 404 | 文件名与预期不符，或改了已发布文件的文件名 | 文件名即 URL，**不要改已发布条目的文件名** |
| 语言按钮点不到对应译文 | 中英文件名不一致（静默失效，不报错） | 两边文件名必须**逐字相同** |
| `/en/does-not-exist/` 显示的是**中文** 404 页 | GitHub Pages 对全站只返回根 `404.html`（静态托管固有限制，ADR-10 已记录） | 已知限制，不是 bug |
| 页面出现裂图 | 图片没放到 `public/images/`，或路径没写绝对路径 `/images/xxx.png` | 检查路径大小写与实际文件名 |
| `pnpm install` 在 CI 失败（本地正常） | 加了依赖但**没提交 `pnpm-lock.yaml`** | 把锁文件一起提交；CI 用 `--frozen-lockfile`，不一致会直接失败 |
| 窄屏「看起来没问题」但手机上有横向滚动条 | 用了 headless 截图判断（<500px 是假象） | 按 R4 的方法测；已知 `/about/` 在 320px 有约 3px 溢出 |
| `git push` 被拒 | 远端有新提交 | `git pull --rebase` 后重推 |

```bash
git push origin main

# —— 回滚 ——
git revert <sha> && git push origin main
```

**必记的 5 条纪律**（摘自 PLAN.md §10.4）
1. **先立项再动手**：改样式 / 加功能要先在 PLAN.md §10.5 登记 `M-<编号>`（纯加内容与改错别字例外）。
2. **只改立项写明的写作用域**，需要扩大就先更新立项行。
3. **不静默偏离 ADR**：要引入客户端 JS、CSS 框架、改 `site`/`base`/内容 schema，**先改 ADR**。
4. **隐私红线优先于进度**：有疑问就停下来问用户，不要「先推上去再删」。
5. **诚实记录**：没跑到的验收就写没跑到，不要写「应该没问题」。
